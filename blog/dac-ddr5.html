DDR5 Power Management at DAC 2024

At DAC 2024, we presented "Watt's Up with DDR5: Formal Verification Framework for Robust DRAM Power Management" - a practical formal methodology for validating DDR5 low-power flows, refresh behavior, and cross-flow interactions from the memory-controller side.

DDR5 brings a real step forward in memory performance and efficiency, but it also makes power management much harder to verify well. Low-power entry and exit, refresh, self-refresh, scheduler coordination, timing windows, and cross-flow interactions all have to behave correctly under strict specification rules. Missing one corner case can mean wasted power, lost bandwidth, or, worse, data integrity risk.

That is why this project focused on building a formal verification framework that could validate these flows exhaustively instead of relying only on directed scenarios. The goal was not just to find bugs, but to create a reusable structure for verifying complex DDR5 power-management behavior in a disciplined way.

Why DDR5 Power Management Is So Tricky

The core challenge is that power-management flows do not live in isolation. DDR5 has strict prerequisites before entering low-power states, tight timing requirements around refresh and power-down operations, and multiple operating modes that interact with normal traffic. From the memory-controller perspective, all of those pieces must line up while still maximizing bandwidth and energy efficiency.

In the talk, we framed the challenge across a few recurring themes:

  • Power-down and self-refresh flows have strict ordering requirements.
  • Timing relationships between controller events must hold across all valid scenarios.
  • The power-management logic interacts heavily with standard scheduler and command flows.
  • Standard checker patterns alone are not enough when the same intent spans multiple states and flows.
The verification strategy centered on an FSM-based reference model plus SVA, with the aim of avoiding design bias, reducing state complexity, and making properties simpler to write and debug.

The Verification Strategy

The foundation of the framework was a set of FSM-based reference models derived from the sequence of events defined by the memory-controller behavior and the DDR5 specification. Those models tracked tasks through externally visible outputs and mapped completed events to abstract states.

That gave us a much cleaner way to express properties. Instead of mirroring the DUT too closely and accidentally inheriting its assumptions, the reference models captured the intended flow at a higher level. This helped reduce design bias and made the resulting SVA checks easier to reason about.

The presentation highlights a refresh-flow model as an example: drain queues, close pages, issue refresh, wait out the required timing, then reopen the system to new work only when the sequence is complete. Once you can track that flow abstractly, the assertions become much more targeted.

Four Checker Families That Mattered

1. Handshake Checkers

Power-management logic communicates with surrounding blocks through request/acknowledge protocols. We used handshake properties to enforce basic but critical rules, such as a request not dropping before acknowledgment and an acknowledgment never appearing without a corresponding request.

One example bug from the talk came from a refresh drain request being dropped too early. An acknowledgment from a previous transaction leaked into the next one, and the DUT treated it as if the new request had already been serviced. That kind of issue is exactly the sort of protocol corruption formal is excellent at exposing.

2. Timing Checkers

DDR5 contains many spec-defined timing windows between events. These checks enforced rules like "event B must not occur if event A happened within the last N cycles," where N comes from configuration or the spec itself.

The deck gives a concrete example around Power Down Entry. In one failing path, the DUT issued PDE on the command bus before the scheduler had been blocked for the required number of cycles. One FSM path implemented the timing rule correctly while another silently skipped it.

3. False Trigger Checkers

These properties guard against flows triggering without the required prerequisite event. In tightly controlled FSM-style behavior, that matters just as much as checking that a legal event eventually happens.

The self-refresh example from the talk is a good illustration: if there is no pending power-state request, the DUT should not issue Self Refresh Entry. A stale internal flag caused one flow to trigger twice even though the request was asserted only once.

4. Prompt Trigger Checkers

This checker family looked at the opposite failure mode: the DUT should not get stuck once the prerequisites to move forward are satisfied. These checks were described in the deck as orthogonal to false-trigger properties, and together they became central to exhaustive flow verification.

The throttling example made that concrete. When the DIMM indicated throttling, the controller should have entered the PDE flow. In one state, the DUT incorrectly waited for unrelated events to complete and never made forward progress even though the real prerequisites had already been met.

Project Scale and Results

The final results slide makes it clear this was not a toy exercise. The project generated:

  • 3 FSM reference models spanning 46 total FSM states
  • 300 assertions
  • 311 constraints
  • 611 functional covers

The effort was carried out by one dedicated engineer at 50% bandwidth over 54 work weeks, for roughly 1,100 engineering hours. The deck also reports an average of around 25 hours per bug, which is a strong signal that the framework was consistently paying off rather than producing isolated wins.

Just as important, the summary slide ties the work back to product impact: successful formal verification of DDR5 power management, a detailed reusable framework for validating those flows, encouraging bug-finding results, and improved controller accuracy and efficiency.

What I Took Away From the Work

The biggest lesson for me was that formal becomes much more scalable when the verification architecture is as intentional as the properties themselves. The FSM reference models were not just a convenience. They were the organizing idea that let the rest of the checker strategy stay readable, reusable, and less vulnerable to design bias.

The second lesson was that cross-flow consistency deserves first-class treatment. Some of the bugs we called out were not classic one-state failures. They came from the same intent being implemented differently in different operating modes or controller states. That is exactly where a carefully structured formal approach can outperform ad hoc checking.

This project reinforced my belief that formal verification is most valuable when it is used early, structurally, and with enough abstraction to make complex behavior understandable instead of merely provable.
