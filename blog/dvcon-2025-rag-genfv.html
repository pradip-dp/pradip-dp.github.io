RAG for Formal-Aware Property Generation

This work was presented at DVCon India 2025, VLSID 2026, and DVCon US 2026. It introduces a RAG-powered GenFV workflow for writing formal testbench code that combines project-specific SVA examples, design documentation, and custom coding guidance to generate better properties than prompt-only LLM usage.

Large language models are already useful for verification-adjacent work, but anyone who has tried to apply them to real formal-property generation quickly runs into the same wall: the more closed-source, specialized, and micro-architectural the problem becomes, the less reliable generic model knowledge feels.

That is exactly the gap this work set out to close. Instead of treating formal property generation as a pure prompting problem, we framed it as a knowledge retrieval plus generation problem. The resulting workflow became the foundation of our DVCon India 2025 paper and later evolved into the VLSID 2026 talk on context-aware property generation.

Why Prompting Alone Plateaus

Our previous DVCon India 2024 work showed that prompt engineering can materially improve formal verification testplanning. But property generation is a tougher target. Writing assertions, constraints, covers, and helper logic for closed-source enterprise designs requires knowledge that frontier models simply do not see in public training data.

That creates a familiar failure mode: simple properties come out looking good, but the moment the design needs deeper context, project norms, or specialized intent, the model begins to hallucinate or over-generalize. Making the prompt longer does not reliably solve that. In many cases it makes the output less stable.

The central idea behind this work was simple: if the task is knowledge intensive, the model should not guess. It should retrieve the right design and verification context before it writes code.

The RAG-Enabled GenFV Framework

The architecture presented in the paper uses a retrieval-augmented generation flow around a normal GenFV loop. The inputs are the RTL, testplan, instructions, and other collateral. The output is formal testbench code, including instrumentation logic and SVA, that can then go into bug finding and proof analysis in VC Formal.

The key difference is that generation no longer relies only on a free-form prompt. Before the LLM produces code, it retrieves relevant material from two knowledge structures:

  • SVA-RAG: a database of key-value pairs where the key is a high-level intent description and the value is a SystemVerilog property plus any useful auxiliary code.
  • Document-RAG: project-specific knowledge such as base specifications, coding guidelines, best-known methods, and other design context the model would otherwise be missing.

That retrieved context is then augmented into the prompt so the model can generate code grounded in real examples and local rules instead of relying on generic memory.

What Goes Into the Database

The SVA database examples shown in the decks are intentionally practical: masked signal equality checks, overflow checks, request-grant patterns, helper logic, timestamps, and contributor metadata. The point is not to build a flashy demo dataset. The point is to give the model reusable formal idioms that reflect how the team actually writes properties.

The document submission adds an important implementation detail here: we populate the RAG with a scraping flow that mines existing formal environments and converts them into structured key-value examples. That reduces the manual burden of curating the knowledge base from scratch.

The same write-up also describes a governance loop for quality. Engineers can choose to check generated properties back into the RAG, those check-ins go through admin review, and accepted updates become available to the wider team on a nightly basis.

Custom Instructions Matter Too

Retrieval alone is not enough. The slide deck calls out a second major lever: custom instruction categories with the biggest impact on output quality. Those instructions include formatting rules, naming conventions, language restrictions, and variable-declaration preferences.

Some of the examples are deliberately strict: keep the property definition and its directive on the same line, do not append arbitrary numbers to generated names, do not use strong and weak keywords, and follow project-specific coding choices rather than whatever the model finds convenient. That turns the system from "a model that can write SVA" into "a model that can write SVA the way this project expects it."

How We Scored Quality

One of the strongest parts of the paper is that it avoids vague quality claims. The submission defines a weighted scoring metric for a complete set of generated assertions:

  • Code Effectiveness with weight 0.4, measuring whether the intended logic is actually verified
  • Code Correctness with weight 0.3, checking for false failures or incorrect behavior
  • Code Quality with weight 0.3, measuring adherence to coding guidelines

That gives a final quality score from 0 to 100, which the work then compares against a human-expertise ladder. In the paper's framing, novice engineers land around 50, intermediate engineers around 70, and experts eventually settle near 95.

What the Early Results Showed

The submission and decks together paint a useful progression. Out of the box, frontier LLMs were landing in roughly the 40 to 50 range. With the RAG infrastructure in place, the system improved toward intermediate-engineer quality once it had access to around 300 quality assertions worth of knowledge and examples.

The paper also notes that after adding 100+ SVAs into the RAG database, the generated assertions improved by about 10% over frontier LLM baselines. The long-term expectation was that a richer database of roughly 500 high-quality SVAs could push the system toward expert-level quality.

That trajectory is what made this work feel real to me. It suggested that quality was not capped by prompt cleverness alone; it could keep rising as the team invested in better examples, richer project context, and stronger feedback loops.

Practical Details That Make It Useful

A few implementation choices from the doc are especially important for real adoption. The flow supports automatic syntax checking of generated properties and can refine them using the compiler error feedback. It also supports a batch mode that consumes an entire testplan and generates multiple properties in one run instead of forcing one-by-one interaction.

Those details matter because they move the system closer to a real engineering workflow. The goal is not just isolated property suggestions. The goal is an AI-assisted pipeline that helps move from testplan to usable formal testbench collateral with less manual friction.

Where This Research Is Headed

The conclusion slide is refreshingly honest. RAG clearly helps with knowledge-intensive FPV work, and the framework is already promising. But the system still struggles when designs become very complex and the verification intent becomes harder to infer.

The future work is exactly where it should be: streamline how the RAG database is enriched and maintained, make the system more capable on harder designs, and keep pushing toward a full AI workflow that spans spec to testplan to testbench. That line also nicely connects this paper back to our earlier DVCon 2024 work and forward to the VLSID 2026 framing.
